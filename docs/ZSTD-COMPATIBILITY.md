# ZSTD 运行库兼容修复（2026-11-13）

## 日志证据与目标

客户端 latest.log:903–905 显示 `NoSuchMethodError: ZstdDecompressCtx.setLongMax(int)`，不是服务端 YAML 关闭 ZSTD，也不等同于原生库提取失败。整合包 Axiom 直接携带旧类，Miku-ZSTD 嵌套 1.5.7-17，而 NetSqueeze 编译使用 1.5.7-26。多个模组共用类名时不保证 NetSqueeze 带入的版本成为实际实现。

## 修复计划

- 消除客户端对新增 setLongMax 方法的硬链接，不重定位 JNI 包、不删除其他模组。
- 在调用本地解码之前，按官方 ZSTD 格式预检帧头、内容大小及窗口；保持 8 MiB 窗口、8 MiB+5 内容大小、单帧无尾随和禁用字典的边界。
- 探测必须运行实际生产解码器；日志区分 Java API/原生库不可用并报告实际类来源。
- 新增帧头边界测试和独立 JVM 旧版 1.5.7-17 运行库测试，复现缺少 setLongMax 的环境，同时消费服务端真实混合压缩夹具。
- 本地只静态检查；不构建/运行测试、不启动游戏，不自动提交推送。GitHub 构建和用户游戏验收后再声明通过。

## 源码完成与待验证项

- 客户端 `ZstdSupport` 及 `ZstdFrameDecoder` 已移除对 `setLongMax` 的静态调用。帧头预检不依赖任何 ZSTD Java 类，在原生函数之前限制窗口和解压大小，保留单帧、无尾随及内容大小一致性检查。
- `ZstdFrameHeaderTest` 覆盖长度编码、2 字节 +256、窗口尾数、截断、无符号溢出、未知大小与字典标志；生产解码器另测大窗口、小内容、尾随与拼接帧。
- `client:check` 已接入 `zstdLegacyCompatibility`，用独立 JVM 把 1.5.7-17 放到类路径首位，过滤 1.5.7-26。测试必须先确认没有 setLongMax，再运行生产探测和服务端实际混合帧夹具，不允许用条件跳过冒充通过。
- 本地仅完成差异和源码静态检查；尚未运行 GitHub 构建或任何测试。现有已安装的 1.5.0 JAR 不包含本次未构建的修改，不能靠重启获得修复。
- 类路径扫描确认 Axiom 内直接存在旧类、Miku-ZSTD 内嵌 1.5.7-17；旧日志不包含类来源，不能仅凭这些证据断言究竟选中了哪个模组的实现。新探测日志会打印实际类来源。
